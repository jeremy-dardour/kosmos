# Sessions 15–20 — Auth v1.1 / PR #32 (2026-07-24 → 2026-07-26)

Six working sessions on branch `auth-v1.1`, merged into one entry: planning
[#30](https://github.com/jeremy-dardour/wedding-planner/issues/30) (backend-validated
session restore), implementing it, two review passes, the sign-in button bug, and
the `AuthProvider` collapse ([#33](https://github.com/jeremy-dardour/wedding-planner/issues/33)).

Continues [session 14](./session-14-2026-07-24-auth-pr29-rebase-cleanup.md), which
rebased PR #29 and wrote the #30 ticket.

## What shipped

- **`GET /api/users/me`** — auth-guarded, verifies the Google token, checks
  `AUTH_ALLOWED_EMAILS`, provisions the `User`, returns `CurrentUserDto`
  (`id`, `email`, `name`, `avatarUrl`). E2E covers `200` / `401` / `403`.
- **Backend-validated web sessions.** Web state becomes authenticated only after
  `/users/me` succeeds; rendered identity comes from the server, never from
  client-decoded Google claims (those are used for expiry only).
- **Fixed the empty sign-in button** — the button rendered, then its own cleanup
  deleted it (`container.replaceChildren()` under StrictMode's double-invoked
  effect wiped the second call's node).
- **Unauthenticated landing** rewritten: no GIS prompt on load, no hardcoded
  filler, all strings in i18next (`auth.landing.*`, en/fr/es).
- **`AuthProvider` collapsed 11 members → 5** with a discriminated `AuthState`;
  `AuthProviderBoundary`, both `useReducer` rerender counters, `AuthViewState`,
  and `restore()` deleted rather than reworked. `@/testing/stub-auth` added.

All boundaries and their rationale are in
[ADR 0007](../adr/0007-web-auth-module-boundaries.md) — not repeated here. It
supersedes the frontend-flow steps in
[V1 Tech Design § Auth](../specs/v1-tech-design.md#auth).

## Decisions not carried by the ADR

- **Backend stays stateless**: no server session, no refresh-token storage. The
  short-lived Google ID token lives in **`sessionStorage`** — refresh in the same
  tab works, persistence ends with the tab.
- **Fake auth's purpose is narrow**: make web + API e2e-testable without Google.
  Multi-user dev switching, moving the allow-list into `MockAuthStrategy`, and
  MSW were each considered and rejected as solving problems this project doesn't
  have.
- The interface collapse **landed on `auth-v1.1` rather than after it** — PR #32
  was not reviewable with the old surface.

## Durable learnings

**Design**

- **A wide interface propagates into everything around it.** Five spec files each
  hand-built the same 11-field literal, and `AuthProviderBoundary` existed only
  because it had 11 methods to forward. Fixing the interface deleted the
  component and the literals; neither needed simplifying on its own. When a
  helper exists to absorb an interface's width, fix the interface.
- **`restore()` was the clearest leaky signature seen so far**: `void |
Promise<void>` hid four facts that lived elsewhere (check `isAuthenticated()`
  after; throws on some failures, returns quietly on others; safe to call twice;
  differs from `login()` only by the prompt). Deleting the method deleted the
  facts.
- **A capability only one adapter needs doesn't belong in the shared interface.**
  `renderSignInButton` forced `FakeAuthProvider` to hand-build a DOM widget — and
  to carry a StrictMode comment for a race it never had.

**React**

- **Memoizing a context value can silently break propagation.** Tried it as an
  optimisation on the auth boundary; context compares by reference, so a stable
  object meant consumers never re-rendered. Two tests caught it. Inviting-looking
  change, no type error.
- `useSyncExternalStore` loops unless `getState()` returns a stable reference
  until the state actually changes.
- Export a built `React.ReactNode`, not a component type, when the value comes
  from a hook — a component type read during render is a new component each pass
  (`react-hooks/static-components`).

**Process**

- **Diagnose from evidence before proposing a fix.** Session 18 proposed a
  loading state and a failure fallback for the empty button, assuming GIS was
  slow or throwing. It resolved successfully every time — the fallback was
  unreachable and a spinner would have shown the same empty box. The network
  panel had the answer (two `gsi/button` iframes, both `ERR_ABORTED`) and was not
  opened.
- **A fresh parallel workspace has an empty dev database** — the setup script
  provisions ports, not schema. Symptom is a `500` from anything touching the DB,
  auth included. Run `pnpm --filter api db:migrate:up` before suspecting code.
- Vitest/Supertest and Playwright need **unsandboxed** execution to bind local
  ports; `pnpm generate:api-types` needs a running API (start it with
  `FAKE_AUTH=true` to skip OIDC discovery).
- Playwright MCP installed (user scope) — used to confirm the landing page in a
  real browser, which is what caught the button bug.
